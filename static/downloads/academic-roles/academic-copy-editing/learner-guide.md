# Module 1 — Editorial scope, style and author queries

## Outcomes

Define the boundary of a copy edit; apply a short style sheet consistently; distinguish a safe correction from an author query.

## Explain and demonstrate

An academic copy editor improves consistency, clarity and correctness while preserving the author’s intended meaning. The role differs from developmental editing, which may restructure an argument, and from subject assessment, which decides whether a technical claim is sound. The same passage can require all three, but responsibility must be explicit. Changing a technical condition without consulting the author can turn a readable sentence into an incorrect instruction.

Start with an editorial brief: audience, document purpose, language convention, referencing style, permitted level of intervention, deadlines and escalation owner. A style sheet records decisions such as heading case, acronym expansion, spelling and number presentation. It is a decision log, not a replacement for a referencing manual. Record exceptions when a vendor product name or quoted title uses a different convention.

### Worked example: edit or query?

Original synthetic sentence: “The learners data are stored secure and all users can delete it after the exam.”

| Issue | Appropriate action | Reason |
|---|---|---|
| “learners data” | Ask whether one or multiple learners; apply possessive form | Number affects punctuation |
| “stored secure” | Change to “stored securely” | Grammar correction preserves meaning |
| “all users can delete” | Query the authorized roles | Security meaning cannot be inferred |
| “after the exam” | Query retention timing and authority | The editor must not invent a policy |

A revised working sentence might read: “Learners’ data are stored securely. [Author query: Which roles may delete the records, and under what approved retention rule?]” The unresolved query stays visible. Do not silently turn “all users” into “administrators” simply because that sounds safer.

## Lab — create an editorial audit trail

**Setup:** Download the synthetic source handout and workbook from the course overview. Use tracked changes or save original and edited plain-text copies for a diff. No client documents are required.

1. Define six style decisions: English variety, heading case, acronym treatment, number convention, figure labels and referencing approach.
2. Edit the first two paragraphs of the supplied handout. Separate mechanical corrections from changes requiring subject confirmation.
3. Create a query log with an ID, original wording, question, reason, owner and status.
4. Add a change that deliberately alters a pass threshold. Ask a peer, or conduct a delayed second review, to identify why this is not an ordinary copy edit.
5. Restore the threshold and mark it for author confirmation if the source itself is ambiguous.

**Expected observations:** The edited version is more consistent, but unresolved policy or technical statements remain queries. **Evidence:** Original, tracked version, clean working copy, style sheet and query log. **Cleanup:** Remove the deliberately altered threshold from the clean copy and retain a labelled training example separately.

## Common pitfalls and teaching decisions

“Standardization” does not mean forcing every discipline into the same technical vocabulary. A synonym can change meaning: “authentication” and “authorization” are not interchangeable. Avoid rewriting a learner’s cultural or linguistic expression unless the agreed editorial purpose requires it. Explain a change in terms of audience understanding and document rules.

## Retrieval and reflection


Can an editor resolve a vague security permission by choosing a plausible role?

No. Query the accountable author or subject expert. A polished but invented rule is a substantive defect.




Why retain both tracked and clean versions?

The clean copy supports reading; the tracked copy supports review and accountability. Preserve a clear version relationship so reviewers know what changed.

# Module 2 — Fact checking and source verification

## Outcomes

Build a claim-to-source ledger; distinguish citation identity from claim support; document uncertainty and correction decisions.

## Explain and demonstrate

A reference can be real yet fail to support the nearby sentence. Source checking therefore has two layers. First, establish identity: title, author, date, publisher and identifier refer to the intended work. Second, inspect the relevant passage to determine whether it supports the claim at the required level of precision. A DOI resolving successfully answers neither question by itself.

Break broad statements into checkable units. “All students learn better with video” combines a population, intervention, comparison and outcome while hiding the conditions. An editor should ask what study, participants, measure and comparison justify “all” and “better.” Do not replace the claim with another unsupported generalization. Record whether the claim is supported, overstated, contradicted or not yet verifiable.

### Worked example: a claim ledger

| Claim | Evidence needed | Editorial decision |
|---|---|---|
| “The course has four modules” | Current course inventory | Verify exact count |
| “All learners improve by 50%” | Defined measure, sample and analysis | Query; do not infer evidence |
| “The API supports method X” | Official documentation for the stated version | Check version and method |
| “A DOI proves reliability” | No identifier guarantees reliability | Correct the conceptual error |

Metadata services can help identify a work and discover updates. They do not replace reading the work or checking publisher notices. If the source is inaccessible, record the access limitation. “Not verified” is an honest status; it is not equivalent to “false.” Keep the quote short and record a section or page locator for the reviewer rather than copying entire documents into the ledger.

## Lab — verify three bounded claims

**Setup:** Use the synthetic handout. Choose three claims that can be checked against freely available primary sources. Use the browser manually; no bulk scraping or authenticated access is necessary.

1. Record the claim verbatim, its location and the exact question to verify.
2. Open the primary source and record its title, URL, relevant section, version or date, and your access date.
3. If a DOI is present, compare its metadata with the reference entry. Check the publisher’s current page for corrections or notices.
4. Write a short support rationale in your own words. Use “not verified” if the actual content is inaccessible.
5. Deliberately attach a valid but irrelevant source to one claim. Explain how an identity-only check would miss the mismatch, then restore the correct mapping.

**Expected observations:** At least one editorial decision should concern the strength or scope of a claim, not just punctuation. **Evidence:** Three ledger rows, a corrected reference and an unresolved-query example. **Cleanup:** Remove irrelevant citations from the release copy and keep only short, necessary excerpts.

## Common pitfalls and teaching decisions

A search snippet may omit qualifications. A vendor’s current documentation may differ from the version used by the course. An AI-generated citation must be opened and checked like any other unverified reference. Do not upload unpublished manuscripts or learner records into an unapproved external service.

## Retrieval and reflection


A DOI resolves and the title matches. Is the factual claim verified?

No. Read the relevant content and compare it with the exact claim. Identity and support are separate checks.




How should an inaccessible source be recorded?

Record the attempted source and access limitation, mark support as not verified and query the author for an accessible or authorized version.

# Module 3 — Accessible technical content

## Outcomes

Edit instructions without changing their technical meaning; create accessible headings and tables; design a release check that catches semantic regressions.

## Explain and demonstrate

Technical editing must preserve the relationship between instructions and results. If a command operates on a file, the document should state the starting folder, prerequisites, expected result and recovery action. An editor should flag an unexplained destructive operation rather than making it look more authoritative. Code, filenames and identifiers are literal data: typographic quotation marks can break a command even when they look attractive.

Accessibility is part of editorial quality. Headings express document structure, not merely visual size. Tables need meaningful headers and should represent relationships rather than page layout. An informative figure needs a text alternative that conveys its purpose; a complex diagram also needs an adjacent explanation. Colour alone should not distinguish “pass” from “fail.”

### Worked example: repair a lab instruction

| Weak instruction | Edited instruction | Remaining subject check |
|---|---|---|
| “Run it and check the result” | “From the exercise folder, run `python lab.py test`.” | Confirm filename and supported Python version |
| “Green means it worked” | “The test runner reports `OK`; colour is optional.” | Confirm expected test count |
| “Fix permissions” | “Record the error and ask the facilitator before changing permissions.” | Identify the authorized recovery procedure |

The edit supplies observable behaviour without inventing privileges. A technically accurate lab should still be executed by a subject reviewer. A successful grammar check is not a lab validation.

## Lab — produce an accessible teaching handout

**Setup:** Work with the supplied synthetic handout and your editor’s styles or semantic Markdown. Keep a copy of the original.

1. Replace manually bolded section labels with real heading levels. Avoid jumping from the document title directly to a fourth-level heading.
2. Convert a list of pass/fail criteria into a two-column table with clear headers and short cells.
3. Describe a three-stage process in text and add a labelled visual. Make the adjacent explanation sufficient without colour or the image.
4. Check code punctuation, paths and expected output against the supplied fixture or a subject-approved run record.
5. Review at 200% zoom and a narrow window. Use the keyboard to reach links and expandable sections in the published preview when available.
6. Introduce a smart quote into a code example, identify it in a literal comparison and restore the original character.

**Expected observations:** Structure remains understandable without visual styling; instructions identify the action, evidence and recovery boundary. **Evidence:** Before/after handout, heading outline, text alternative and technical-query log. **Cleanup:** Remove the deliberate smart-quote defect and any unresolved test claim from the clean release copy.

## Common pitfalls and teaching decisions

An automated accessibility checker cannot decide whether a diagram’s explanation is useful. Alt text that repeats a filename provides little meaning. Do not label the whole document “WCAG compliant” from a handful of checks; report the observed checks and remaining review scope. For equations, provide readable notation and a prose explanation of variables rather than an image alone.

## Retrieval and reflection


Should alt text list every visual detail of a complex diagram?

Use a concise purpose-focused alternative and provide the detailed relationships in nearby text. Avoid forcing a long technical explanation into a single label.




What can a copy editor conclude after checking the spelling of a command?

Only that the literal text matches the checked source. Execution, permissions and technical correctness still need appropriate validation.

# Module 4 — Editorial release capstone

## Outcomes

Integrate the course evidence into a reproducible editorial handover; apply an analytic rubric; identify a specific improvement after feedback.

## Scenario and deliverable

Edit an original 700-word teaching handout supplied by your assessor or written for this exercise. Include one numerical example, one table, two genuine references and three deliberately ambiguous claims. Deliver tracked and clean versions, a style sheet, a claim ledger and a release recommendation that separates resolved edits from author decisions.

This capstone is a public portfolio brief. It is not a secure exam. Formal assessment requires an assigned assessor, an approved private submission channel and confirmed assessment arrangements. Do not upload learner records or controlled institutional questions to a public repository.

## Worked example: plan the evidence before the performance

A strong submission makes a claim, shows the relevant artifact and explains why the artifact meets the criterion. For example, “the task has been checked” is weaker than a dated run record naming the fixture, environment and expected result. For editorial work, show the original wording, the query or edit, its justification and the release decision. For teaching work, show the outcome, the task and the learner evidence it produces.

| Stage | Time budget | Observable output |
|---|---|---|
| Plan and check prerequisites | 45 minutes | Scope, outcome and readiness checklist |
| Produce the task and worked example | 75 minutes | Reproducible learner materials |
| Rehearse and deliver | 60 minutes | Observed performance and feedback |
| Moderate and revise | 60 minutes | Rubric, correction and final reflection |

These are planning estimates, not measured completion times. Pause when a prerequisite is missing and record the adjustment rather than rushing through unverified work.

## Lab — assemble and defend the portfolio

1. Gather the three earlier module artifacts. Label each with the course ID, module, version and date; remove unnecessary personal information.
2. Use the downloadable workbook to map each artifact to an outcome and acceptance criterion.
3. Prepare the role-specific capstone above. Keep its scope small enough to verify every important claim.
4. Rehearse with a peer or record a self-review. If recording another person, obtain permission and use an approved private location; a written observation is an alternative.
5. Introduce one controlled defect in a labelled copy. Demonstrate how a test, source check or rubric detects it, then restore the correct version.
6. Score the evidence against the rubric below. An assessor should reproduce at least one technical or editorial check and explain any disagreement.
7. Revise the weakest criterion and submit a short change record. Retain the initial and revised versions so the improvement is visible.

**Expected observations:** Every scored claim has observable evidence, and the corrected artifact passes the same check that exposed the defect. **Evidence:** The four artifacts listed on the course overview, a rubric record and a reflection. **Cleanup:** Remove faulty release copies and temporary files; retain only the agreed evidence in the approved workspace.

## Assessment rubric

This is the proposed Academy pilot standard. Score each criterion from 0 to 4 and calculate `weight × level / 4`. Level 0 means absent evidence; 1 means major errors; 2 means partially working or incompletely verified; 3 means correct, reproducible and appropriately explained; 4 adds justified transfer and diagnosis of a meaningful fault.

| Criterion | Weight | Evidence required for level 3 |
|---|---|---|
| Subject correctness | 30% | Correct reasoning and outputs against explicit requirements |
| Role-specific performance | 25% | A coherent editorial handover aligned with its audience and outcome |
| Verification and reproducibility | 20% | Traceable checks, environment or source details, and a demonstrated repair |
| Accessibility and clarity | 15% | Structured materials, readable visuals and equivalent text explanations |
| Safe professional handover | 10% | Synthetic or authorized data, source attribution and unresolved issues recorded |

**Pilot completion threshold:** at least 75/100, with subject correctness and verification each at level 3 or above, and all critical conditions resolved. This is not a vendor examination pass mark. A browser self-check does not issue a certificate or record an official grade.

**Critical condition:** Fabricated citations, silently changed assessment meaning or release of personal data prevents release.

## Feedback, moderation and reassessment

Give feedback using an observed artifact, the relevant criterion and one concrete next action. Where two assessors disagree, compare the same evidence and record the reason for the final decision. Do not average unexplained scores to hide disagreement. A reassessment should target the missing capability with a fresh equivalent task, followed by rechecking the affected criteria. Follow the commissioning institution's approved appeals process for formal delivery.

## Retrieval and reflection


Can a polished presentation compensate for incorrect subject reasoning?

No. Subject correctness has a minimum required level and cannot be offset by attractive formatting. Correct the reasoning and verify the revised artifact.




What distinguishes a self-check from formal assessment here?

A self-check supports practice. Formal assessment requires an authorized assessor, controlled evidence handling, recorded decisions and confirmed institutional arrangements. This public course does not create those records automatically.
