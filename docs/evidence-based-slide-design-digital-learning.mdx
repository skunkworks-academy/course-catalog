# Evidence-Based Slide Design for Digital Learning

**Course ID:** LXD-SLD-201  
**Estimated effort:** 30-36 hours  
**Level:** Intermediate  
**Audience:** Instructional designers, trainers, lecturers, teachers, learning-experience designers, technical course developers, subject-matter experts, enablement teams and digital-content producers  
**Assessment model:** Twelve theory modules, eight practical labs, design critiques, formative checks, a final knowledge check, an evidence portfolio and a capstone learning-product build  
**Primary production tools:** PowerPoint, Google Slides, Articulate Storyline, Adobe Captivate or an equivalent slide-based authoring environment  

## Course purpose

Slideware is not merely a presentation format. In digital learning it can function as a **learning interface**, a **visual explanation system**, a **practice environment**, a **narrative scaffold**, an **assessment surface** and a **trackable learning object**.

This course develops the capability to move from a content dump to a deliberately engineered learning experience. Learners will use research-based learning principles, cognitive-load management, multimedia learning, visual communication, accessibility, interaction design and learning-technology standards to create slide-based experiences that are purposeful, usable and measurable.

The course is deliberately **build-oriented**. Every major concept ends in an artefact, design decision or production task. By the end of the course, the learner will not only be able to explain why effective learning slides work; they will be able to **design, build, test, remediate and publish** a complete slide-based learning module.

## Evidence basis and source handling

This course was designed from the supplied research-oriented framework and then expanded with current authoritative product and standards guidance.

The supplied material establishes these core ideas:

- start from learning purpose rather than decoration;
- use manageable chunks and generally one main idea per slide;
- map slide content to learning outcomes and assessment;
- combine words and purposeful visuals rather than text alone;
- use questions, activities and retrieval opportunities to keep learners active;
- storyboard before production;
- design for accessibility and inclusion;
- test, gather feedback and iterate;
- prepare slide-based learning for LMS delivery and learning analytics where required.

A critical distinction used throughout this course is that **principles are not rigid formatting rules**. For example, “one idea per slide,” “5-7 lines,” and “24pt or larger” are useful design heuristics, not universal laws. The correct design depends on viewing context, complexity, device, learner task and accessibility requirements.

The course also avoids treating visual, auditory or kinesthetic “learning styles” as fixed learner types. Multiple representations can be valuable, but they should be chosen because they support the task, reduce barriers or clarify the content—not because a learner has been assigned a permanent style label.

## Capability outcome

By the end of this course you will be able to:

- convert a learning requirement into measurable outcomes, an assessment plan and a slide architecture;
- decide what belongs on a slide, in narration, in notes, in an activity or outside the deck entirely;
- manage intrinsic complexity and reduce unnecessary cognitive load;
- apply multimedia-learning principles such as coherence, signaling, contiguity, segmenting and modality deliberately;
- create storyboards that define purpose, screen composition, narration, interaction, accessibility and tracking before production;
- design typography, spacing, hierarchy, grids and visual rhythm for readable digital learning;
- build diagrams, process visuals, comparison graphics, data displays and concept maps that teach rather than decorate;
- script and synchronize narration, audio, video and animation without duplicating or overloading the visual channel;
- create retrieval practice, scenarios, branching decisions, guided notes and feedback loops;
- build accessible slides with meaningful titles, logical reading order, alt text, captions, keyboard-friendly interaction and sufficient contrast;
- make informed tool choices across PowerPoint, Google Slides, Storyline, Captivate and comparable platforms;
- design LMS publishing and tracking strategies using SCORM and/or xAPI concepts where appropriate;
- run design reviews, accessibility checks, usability tests and learning-quality evaluation;
- build and defend a complete slide-based learning product using evidence-led design decisions.

## The production loop used throughout the course

Use this loop for every learning asset:

1. **Define the capability.** What must the learner be able to do after the experience?
2. **Define evidence.** What performance, answer or artefact will prove that capability?
3. **Map the learning sequence.** What must the learner notice, understand, practise and retrieve?
4. **Choose the representation.** Decide between text, diagram, worked example, animation, audio, video, interaction or external resource.
5. **Storyboard.** Define each screen before polishing it.
6. **Build the minimum useful version.** Prioritise instructional function before decoration.
7. **Check accessibility.** Validate structure, contrast, reading order, alternatives and interaction.
8. **Test with users.** Look for comprehension, navigation and attention failures.
9. **Measure.** Use assessment evidence, completion data and learner behaviour where available.
10. **Iterate.** Remove friction and improve the learning path.

## Module 1 - Slideware as a learning system

### 1.1 The slide is not the lesson

A slide is one component in a learning system. The learning experience may also include:

- facilitator explanation;
- narration;
- learner notes;
- demonstrations;
- job aids;
- simulations;
- discussion;
- practice;
- assessment;
- feedback;
- external reading;
- LMS navigation and progress tracking.

Poor slide design often begins when designers try to make the slide carry all of these functions at once.

A better question is:

> What is the smallest useful role this slide should perform in the learner's journey?

### 1.2 Common slide functions

| Slide function | Primary purpose | Typical content |
|---|---|---|
| Orientation | Establish context and direction | Agenda, learning outcome, section map |
| Explanation | Build a mental model | Diagram, annotated example, short explanatory text |
| Demonstration | Show how something is done | Screen sequence, worked example, process animation |
| Comparison | Reveal similarities or differences | Matrix, paired examples, decision table |
| Retrieval | Make the learner recall | Question, prompt, blank diagram, flash challenge |
| Practice | Require a decision or action | Scenario, drag-and-drop, branching choice |
| Feedback | Correct or reinforce thinking | Explanation, worked solution, misconception repair |
| Reflection | Encourage synthesis | Prompt, journal cue, confidence check |
| Transition | Signal structure | Section title, progress marker, recap |

### 1.3 Purpose before decoration

Visual polish cannot rescue a slide that has no instructional purpose. Before designing any screen, complete this sentence:

```text
This slide exists so the learner can ______________________________.
```

If the sentence describes what the **designer wants to say** instead of what the **learner needs to process or do**, rewrite it.

### 1.4 The content-dump failure pattern

A content dump usually has these characteristics:

- the slide title names a topic but not a learning purpose;
- paragraphs duplicate the speaker or narration;
- every important fact is given equal visual weight;
- decorative stock imagery consumes space but adds no explanatory value;
- learners have no reason to retrieve, decide, predict or practise;
- assessment appears at the end but was not considered during design.

### 1.5 Build for use context

A deck projected in a classroom, a self-paced mobile module and a narrated Storyline lesson have different constraints.

Document the context before production:

```text
Primary learner:
Viewing mode: live / self-paced / blended
Primary device: desktop / tablet / mobile / projector
Audio available: yes / no / optional
Expected session length:
Learner action required:
Assessment method:
Accessibility target:
Tracking requirement:
```

### Formative design check

For three existing slides, write one sentence describing the learner-facing purpose of each. If you cannot write a clear purpose without using words such as “show,” “cover,” or “tell,” the slide may be presenter-centred rather than learner-centred.

## Practical Lab 1 - Diagnose and redesign a weak learning slide

### Scenario

You receive a slide titled **“Cybersecurity Awareness”** containing 12 bullets, two decorative stock photos, a five-line definition and a paragraph copied from a policy document.

### Tasks

1. Identify the intended learning outcome.
2. Mark every element as essential, supportive, redundant or decorative.
3. Identify likely cognitive-load problems.
4. Decide what should remain on-screen and what should move to narration, notes or a resource.
5. Redesign the slide as a short sequence of two to four screens.
6. Add one learner action: prediction, retrieval question, classification or decision.
7. Write a short rationale explaining each design decision.

### Acceptance criteria

- each redesigned slide has one dominant purpose;
- visual hierarchy makes the intended processing order obvious;
- nonessential content is removed or relocated;
- the learner performs at least one meaningful cognitive action;
- the rationale references learning rather than aesthetics alone.

## Module 2 - Learning outcomes, backward design and alignment

### 2.1 Start from observable capability

Effective slide design begins before the first slide is drawn.

A weak outcome says:

```text
Understand phishing.
```

A stronger outcome says:

```text
Given five email examples, classify likely phishing indicators and justify the escalation decision using the organisation's reporting policy.
```

The stronger outcome immediately tells the designer what kind of explanation, practice and assessment the learner needs.

### 2.2 Backward design

Use this sequence:

1. What must the learner be able to do?
2. What evidence would prove it?
3. What knowledge or mental model is prerequisite?
4. What practice will prepare the learner?
5. What slide sequence will support that practice?

### 2.3 Alignment matrix

Build a matrix before production:

| Outcome | Evidence | Learning activity | Slide support | Assessment |
|---|---|---|---|---|
| Classify three risk levels | Correct classification with rationale | Worked examples + scenario sorting | Decision criteria + examples | Scenario classification |
| Build a process map | Complete process with dependencies | Guided mapping | Step sequence + visual conventions | Learner-created map |
| Troubleshoot an error | Correct root cause and next action | Diagnostic case | Evidence ladder + decision tree | Case response |

### 2.4 Content priority

Classify content into four levels:

- **Must perform** - directly required for the capability.
- **Must know** - required to perform correctly.
- **Should know** - useful context or transfer knowledge.
- **Could know** - enrichment or reference content.

Slides should privilege the first two categories. “Could know” material usually belongs in notes, optional resources or reference material.

### 2.5 Evidence before exposition

If the final assessment requires the learner to design, diagnose, compare, configure or create, a purely explanatory slide deck is misaligned. Learners need practice that resembles the desired performance.

### Formative design check

Choose one topic you teach. Rewrite the outcome using:

```text
Given [conditions/resources], the learner will [observable action] to [quality/standard].
```

Then write the evidence that would convince an assessor the learner can actually do it.

## Module 3 - Cognitive load and multimedia learning

### 3.1 Working memory is limited

Learning design must account for the limited capacity of working memory. Complex material can overwhelm learners when too many interacting elements must be processed simultaneously.

For practical design, separate two concerns:

- **intrinsic complexity** - difficulty inherent in the task and the learner's prior knowledge;
- **extraneous load** - difficulty caused by the way information is presented.

You often cannot remove the intrinsic complexity of a difficult task, but you can sequence it, pre-train prerequisite concepts and reduce unnecessary presentation burden.

### 3.2 Chunking is instructional sequencing

Chunking is not simply “make the paragraph shorter.” A useful chunk represents a coherent unit the learner can process and connect to prior knowledge.

Examples:

- one stage of a troubleshooting process;
- one relationship in a system diagram;
- one decision criterion;
- one worked step;
- one misconception and its correction.

The “one idea per slide” rule is therefore best treated as a strong default heuristic.

### 3.3 Multimedia learning principles

Use these principles as design questions:

**Coherence:** Can anything be removed because it does not support the learning goal?  
**Signaling:** Have you highlighted the structure, key relationship or next step?  
**Spatial contiguity:** Are labels close to the visual elements they describe?  
**Temporal contiguity:** Do related narration and animation occur together?  
**Segmenting:** Can the learner process the explanation in meaningful stages?  
**Pre-training:** Does the learner know the names and roles of key components before a complex explanation begins?  
**Modality:** Would spoken explanation plus a diagram be more useful than a diagram plus a paragraph that duplicates the narration?  
**Redundancy control:** Are identical words unnecessarily competing across narration and on-screen text?

### 3.4 Dual-channel design is not “add more media”

Combining words and pictures can improve explanation when the channels are coordinated. It does not mean adding an image, video and audio track to every slide.

Purposeful multimedia answers one of these questions:

- What relationship is difficult to explain with words alone?
- What process is easier to see than to describe?
- What visual pattern should the learner notice?
- What should be narrated because placing it as text would overload the screen?

### 3.5 Signaling and progressive disclosure

A complex diagram can be taught by revealing:

1. the whole system;
2. one subsystem;
3. a highlighted path;
4. a failure point;
5. the completed model again.

The animation is useful because it controls attention, not because movement is inherently engaging.

### 3.6 Worked examples and fading

For procedural or problem-solving content:

1. show a fully worked example;
2. explain why each step occurs;
3. present a partially completed example;
4. require the learner to complete more of the work;
5. move to an independent problem.

This creates a bridge from explanation to performance.

## Module 4 - Storyboarding and learning-experience UX

### 4.1 Storyboards prevent expensive rework

A storyboard separates **instructional decisions** from **production decisions**. It allows reviewers to challenge sequencing, interaction and messaging before time is spent polishing graphics or recording audio.

### 4.2 Storyboard fields

Use a storyboard with at least these fields:

```text
Screen ID:
Learning purpose:
On-screen title:
On-screen text:
Visual / diagram:
Narration / facilitator notes:
Learner action:
Feedback:
Accessibility notes:
Tracking event:
Source / rights information:
Reviewer notes:
```

### 4.3 Screen states

Interactive learning often requires multiple states for what appears to be one slide:

- initial state;
- hover or focus state;
- selected state;
- correct feedback;
- incorrect feedback;
- completion state;
- remediation state.

Storyboard these states rather than assuming the authoring tool will solve them automatically.

### 4.4 Navigation architecture

Choose deliberately between:

- linear sequence;
- menu-driven exploration;
- branching scenario;
- hub-and-spoke exploration;
- progressive unlock;
- adaptive remediation.

Navigation should serve the learning task. For example, a compliance lesson may require a controlled sequence, while a product-reference module may benefit from non-linear exploration.

### 4.5 Progress and orientation

Learners need to know:

- where they are;
- what remains;
- what they are expected to do;
- how to recover from a mistake;
- whether an action has been completed.

Use section labels, progress indicators, consistent controls and explicit completion feedback.

### 4.6 Design the empty states

Do not only storyboard the happy path. Plan:

- no answer selected;
- incorrect answer;
- partially completed interaction;
- video unavailable;
- audio unavailable;
- keyboard-only navigation;
- small-screen layout;
- resumed session.

## Module 5 - Typography, layout, hierarchy and visual rhythm

### 5.1 Typography is an attention system

Typography should establish:

1. what the learner notices first;
2. what is supporting detail;
3. what is an instruction;
4. what is an example;
5. what is metadata or reference material.

### 5.2 Practical typography defaults

For conventional presentation viewing, use large, readable type. A useful baseline is approximately **24pt or larger for primary body text** when the slide may be viewed at distance, while Microsoft accessibility guidance also recommends large sans-serif fonts and notes 18pt or larger as an accessibility-oriented baseline for PowerPoint. The correct value depends on display mode, screen size and content density.

Use:

- a restrained number of typefaces;
- consistent title, subtitle, body and caption styles;
- generous line spacing;
- left alignment for longer text blocks;
- bold weight for emphasis rather than repeated colour changes;
- sentence case where practical.

Avoid:

- dense all-caps paragraphs;
- long centred paragraphs;
- tiny footnotes that contain essential content;
- underlining that can be confused with links;
- decorative fonts for body copy.

### 5.3 Grid and alignment

Use a repeatable grid. For example:

```text
12-column canvas
Outer margin: consistent
Title zone: fixed
Content zone: flexible
Footer/progress zone: fixed
```

Alignment creates visual relationships. If two elements are meant to be compared, align them. If they are unrelated, do not accidentally imply a relationship through proximity.

### 5.4 Whitespace is functional

Whitespace can:

- separate groups;
- reduce visual competition;
- create focus;
- provide space for annotation;
- improve readability;
- make progression clearer.

### 5.5 Contrast and emphasis

Use contrast through:

- size;
- weight;
- position;
- whitespace;
- shape;
- controlled colour.

Do not depend on colour alone to indicate meaning.

### 5.6 The 5-7 line heuristic

Limiting text to roughly 5-7 lines can be a useful discipline for presentation slides, but it is not a learning-science law. The more important rule is that on-screen text should support the intended processing task without becoming a transcript or mini-book.

## Module 6 - Visual explanation, diagrams and data storytelling

### 6.1 Use visuals to explain relationships

A learning visual should answer a question that plain text answers poorly.

Useful visual forms include:

- process flows;
- system architecture diagrams;
- timelines;
- concept maps;
- cause-and-effect diagrams;
- comparison matrices;
- before/after examples;
- annotated screenshots;
- decision trees;
- layered models;
- data charts.

### 6.2 Choose the visual by relationship

| Relationship to teach | Useful visual form |
|---|---|
| Sequence | Timeline, numbered process, flow |
| Hierarchy | Tree, nested boxes, pyramid when genuinely hierarchical |
| Comparison | Side-by-side, matrix, aligned examples |
| Cause and effect | Causal chain, fishbone, influence map |
| Part-to-whole | Layered architecture, exploded view |
| Decision | Decision tree, criteria matrix |
| Trend | Line chart |
| Magnitude | Bar chart |
| Distribution | Histogram or dot plot |

### 6.3 Annotate, do not decorate

A screenshot is not automatically instructional. Add:

- a crop that removes irrelevant UI;
- a highlight around the target element;
- a concise label;
- a step number;
- a callout explaining why it matters.

### 6.4 Data graphics

When showing data:

- define the decision the data should support;
- remove chart junk;
- label the key comparison directly;
- avoid misleading axes;
- use consistent scales;
- make the intended takeaway visible without hiding uncertainty.

### 6.5 Visual rights and provenance

Maintain a media register with:

```text
Asset ID:
Source URL or repository:
Creator:
Licence / permission:
Attribution required:
Modification allowed:
Alt text:
Date retrieved:
```

Do not treat search-engine image results as permission to reuse an image.

## Module 7 - Narration, audio, video and motion

### 7.1 Narration should add value

Narration is useful when it:

- explains a visual relationship;
- provides context not needed on-screen;
- guides attention;
- models reasoning;
- humanises a scenario;
- supports a demonstration.

It is usually weak when it simply reads paragraphs already displayed on screen.

### 7.2 Script before recording

A narration script should identify:

```text
Screen ID:
Narration text:
Visual cue:
Pause point:
Interaction cue:
Pronunciation note:
Caption text:
Audio description need:
```

### 7.3 Synchronisation

When narration refers to a visual element, the relevant element should appear at approximately the same time. Avoid showing a complete busy diagram while narration discusses one tiny part unless the learner is clearly signaled to the current area.

### 7.4 Motion as explanation

Use animation to show:

- change over time;
- sequence;
- movement through a system;
- transformation;
- dependency;
- progressive construction.

Avoid motion used only to make the slide feel “dynamic.” Unnecessary motion can distract, disorient or create accessibility problems.

### 7.5 Captions and alternatives

For meaningful audio/video:

- provide synchronized captions;
- provide a transcript when useful;
- ensure essential visual information is available to learners who cannot see it;
- ensure essential audio information is available to learners who cannot hear it;
- avoid interactions that require sound alone to know whether an answer was correct.

### 7.6 Media fallback

Design for media failure:

```text
If audio is muted → captions/transcript still carry meaning.
If video cannot play → transcript or equivalent content is available.
If animation is unavailable → static end-state still communicates the model.
```

## Module 8 - Interaction, retrieval practice and feedback

### 8.1 Activity is not the same as learning

Clicking, dragging and tapping can create activity without meaningful cognition. An interaction is instructionally useful when the learner must:

- retrieve;
- distinguish;
- classify;
- predict;
- choose;
- sequence;
- explain;
- diagnose;
- construct;
- reflect.

### 8.2 Retrieval practice

Instead of repeating a definition, ask the learner to recall it or apply it.

Example:

```text
Which of these slide designs is most likely to overload the learner, and why?
```

The explanation after the answer is as important as the score.

### 8.3 Feedback design

Weak feedback:

```text
Incorrect. Try again.
```

Stronger feedback:

```text
Not yet. This option adds a second paragraph that duplicates the narration. The issue is redundant verbal information, not the number of colours. Re-examine the slide and choose the version that preserves the diagram while moving explanation into narration.
```

### 8.4 Scenario-based learning

A useful scenario contains:

- a role;
- a goal;
- incomplete information;
- a decision;
- consequences;
- feedback tied to the decision criteria.

### 8.5 Gamification with purpose

Points, badges and timers are optional. Use them only when they support the intended behaviour.

More durable gamification patterns include:

- progressive mastery;
- challenge levels;
- visible competence milestones;
- branching consequence;
- meaningful retries;
- scenario realism;
- personal best or practice streak where appropriate.

### 8.6 Guided notes

Guided notes can increase active processing when learners fill key relationships, label diagrams or complete structured examples rather than transcribing the whole presentation.

## Module 9 - Accessibility and inclusive slide design

### 9.1 Accessibility is part of design quality

Accessibility should be planned at storyboard stage, not added after development.

WCAG 2.2 is the current W3C Recommendation for web accessibility and provides a useful reference point for web-delivered learning. Slide tools also have platform-specific accessibility capabilities and limitations.

### 9.2 Slide titles

Every slide should have a unique, meaningful title where the platform supports it. Titles help learners, screen-reader users and authors understand structure and location.

If a visible title does not fit the visual design, some tools allow a title to remain available to assistive technology while being positioned off-canvas or hidden visually. Verify that the technique remains accessible in the published output.

### 9.3 Reading order

Visual position does not guarantee screen-reader order.

Check:

- title first;
- instruction before response controls;
- labels before related values where appropriate;
- explanatory content in logical sequence;
- decorative elements excluded from reading order when supported.

PowerPoint provides Accessibility Checker and Reading Order tools. Google Slides also provides screen-reader support, tab/read order controls and alt-text workflows.

### 9.4 Alternative text

Good alt text communicates the **meaning and function** of a visual in context.

For a decorative image, mark it decorative when the platform supports that behaviour.

For a complex diagram, a short alt description may not be enough. Provide an equivalent structured explanation in nearby text, notes or an accessible companion resource.

### 9.5 Colour and contrast

Do not encode meaning by colour alone.

For example, replace:

```text
Green = pass
Red = fail
```

with:

```text
✓ Pass
✕ Fail
```

and also ensure sufficient contrast.

### 9.6 Captions and transcripts

Provide captions for meaningful spoken audio. Provide transcripts when they improve access or review. For important visual-only information in video, provide an equivalent description.

### 9.7 Keyboard and focus

Interactive slide-based learning must be usable without a mouse where the delivery platform supports keyboard interaction.

Test:

- tab order;
- visible focus;
- Enter/Space activation;
- focus after feedback opens;
- focus after modal/layer closes;
- skip or exit behaviour;
- no keyboard traps.

### 9.8 Tool-specific checks

**PowerPoint:** use built-in layouts where practical, unique titles, Accessibility Checker, logical reading order, meaningful links, alt text and captions.  
**Google Slides:** verify screen-reader order, alt text, captions and keyboard navigation.  
**Storyline:** validate the published learner experience against current Articulate accessibility guidance and the product's current Accessibility Conformance Report.  
**Captivate:** use current accessibility features for slides, objects, interactive components, widgets and quizzes, then test the published output with assistive technology.

### 9.9 Accessibility testing matrix

```text
Automated checker: pass / issues
Keyboard-only test: pass / issues
Screen-reader smoke test: pass / issues
Colour/contrast test: pass / issues
Zoom/reflow or responsive test: pass / issues
Captions/transcript review: pass / issues
Alternative text review: pass / issues
Interaction focus review: pass / issues
```

## Practical Lab 7 - Accessibility remediation sprint

### Input

Take a 10-slide deck or prototype and intentionally include at least six accessibility defects such as:

- missing slide titles;
- poor reading order;
- low contrast;
- colour-only meaning;
- missing alt text;
- vague hyperlink text;
- missing captions;
- inaccessible interaction order.

### Tasks

1. Run the platform's accessibility checker where available.
2. Record every issue in a defect log.
3. Remediate titles and reading order.
4. Add meaningful alt text or equivalent descriptions.
5. Correct contrast and non-colour indicators.
6. Add captions/transcripts where needed.
7. Test keyboard navigation.
8. Perform a screen-reader smoke test where available.
9. Record any platform limitation that could not be remediated in-authoring.
10. Produce a before/after accessibility report.

### Acceptance criteria

- defects are documented, not merely fixed silently;
- reading order follows instructional intent;
- essential visuals have equivalents;
- interaction is keyboard operable where the platform supports it;
- unresolved limitations are documented with a mitigation plan.

## Module 10 - Authoring across PowerPoint, Google Slides, Storyline and Captivate

### 10.1 Choose the tool from the learning need

Do not select an authoring tool because it is fashionable. Select it because it supports the required interaction, publishing, accessibility, collaboration, maintenance and tracking model.

### 10.2 Tool-fit matrix

| Need | PowerPoint | Google Slides | Storyline | Captivate |
|---|---|---|---|---|
| Rapid visual deck | Strong | Strong | Possible | Possible |
| Real-time collaboration | Moderate/strong depending on environment | Strong | Review-oriented | Review-oriented |
| Complex branching | Limited to moderate | Limited | Strong | Strong |
| Rich state-based interaction | Moderate with triggers | Limited | Strong | Strong |

| Fine-grained learning tracking | Limited natively | Limited natively | Strong via publishing options | Strong via publishing options |
| Accessible presentation workflows | Strong tool support, output dependent | Strong tool support, output dependent | Current accessibility support must be tested | Current accessibility support must be tested |

### 10.3 PowerPoint production patterns

Use:

- slide masters and layouts;
- theme fonts and theme colours;
- consistent placeholders;
- Selection/Reading Order panes;
- hyperlinks and action buttons;
- Morph/animation only when it explains change;
- speaker notes for scripts and facilitator guidance;
- Accessibility Checker before delivery.

Use:

- master/theme layouts;
- collaborative commenting and version history;
- linked objects where appropriate;
- alt text and accessible order;
- captions during presentation when appropriate;

- question banks;

Plan:

- responsive layouts/components;
- slide/object accessibility;
- interactive components and quiz accessibility;
- timeline behaviour;
- project-level navigation;
- publishing and LMS configuration.

## Module 11 - LMS publishing, SCORM, xAPI and learning analytics

### 11.1 Publishing is part of instructional design

A learning object that works in preview but fails to report completion in the LMS is not production-ready.

Define before development:

- LMS target;
- completion rule;
- score rule;
- pass threshold;
- resume behaviour;
- attempt policy;
- learner identifier handling;
- analytics requirement;
- accessibility and browser support expectations.

### 11.2 SCORM concept model

SCORM packages are commonly used to launch web-based learning content from an LMS and communicate completion, score and related runtime data.

Your publishing checklist should include:

```text
Package type/version required by LMS
Launch file
Completion criteria
Success/pass criteria
Score range
Resume/suspend behaviour
Attempt handling
Window/frame behaviour
Cross-domain constraints
QA test account
```

Do not assume every LMS interprets completion and success identically. Test the exact package in the target LMS.

### 11.3 xAPI concept model

xAPI describes learner experiences using structured statements. A useful human-readable planning form is:

```text
Actor + Verb + Object + Result + Context
```

Example design intent:

```text
Learner completed Slide Design Accessibility Audit
result.score.scaled = 0.92
context = LXD-SLD-201 / Practical Lab 7
```

The current xAPI specification is version 2.0. Treat statement design as part of the measurement architecture rather than logging every click simply because it is possible.

### 11.4 Track meaningful evidence

Useful events may include:

- module started;
- scenario completed;
- assessment submitted;
- mastery threshold reached;
- remediation triggered;
- capstone artefact submitted;
- learner confidence check;
- optional resource opened when that event answers a defined analytics question.

Avoid collecting unnecessary behavioural or personal data.

### 11.5 Analytics questions first

Before defining events, write the question:

```text
Are learners failing because they do not understand visual hierarchy, or because the interaction instructions are unclear?
```

Then decide what evidence would answer it.

### 11.6 Learning telemetry schema

```text
Event name:
Learning question supported:
Actor identifier:
Verb:
Object:
Result:
Context:
Timestamp:
PII/sensitivity classification:
Retention period:
Dashboard or analysis use:
```

## Module 12 - Evaluation, usability testing and continuous improvement

### 12.1 Test learning, not only appearance

A polished deck can still fail if learners:

- cannot find the next action;
- misunderstand a diagram;
- skip important content;
- misinterpret feedback;
- fail the transfer task;
- cannot operate the interaction with a keyboard;
- experience audio or caption problems;
- reach the end without knowing what they learned.

### 12.2 Three-layer quality model

**Layer 1 - Content correctness**  
Is the information accurate, current and properly sourced?

**Layer 2 - Learning effectiveness**  
Does the sequence help the learner achieve the intended capability?

**Layer 3 - Experience quality**  
Can the learner navigate, perceive, operate and understand the experience with minimal friction?

### 12.3 Review roles

Use separate review lenses:

- subject-matter expert;
- instructional designer;
- visual/UX reviewer;
- accessibility reviewer;
- technical/LMS reviewer;
- pilot learner.

A single reviewer rarely catches every class of defect.

### 12.4 Usability test protocol

Use a short task-based protocol:

```text
Participant profile:
Task:
Success condition:
Time on task:
Observed hesitation:
Navigation error:
Misinterpretation:
Accessibility issue:
Learner quote:
Severity:
Recommended change:
```

### 12.5 Comprehension probes

After a visual explanation, ask the learner to:

- explain the relationship in their own words;
- reconstruct the process;
- choose the correct example;
- identify the next step;
- diagnose a failure;
- transfer the rule to a new scenario.

If they can repeat the slide but cannot perform the transfer, the design has not yet achieved the capability outcome.

### 12.6 Analytics interpretation

Possible signals:

| Signal | Possible interpretation | Next validation step |
|---|---|---|
| High replay rate on one segment | Confusing or valuable content | Interview/pilot test the segment |
| High incorrect-answer rate | Misconception or unclear question | Review distractors and prerequisite knowledge |
| Rapid click-through | Content may be too easy or ignored | Add retrieval probe; inspect completion evidence |
| High abandonment | Length, friction, relevance or technical issue | Check session data and user feedback |
| Repeated backtracking | Orientation or comprehension problem | Observe learners using the module |

Analytics do not explain cause by themselves. Combine them with observation, learner feedback and assessment evidence.

### 12.7 Definition of done

A slide-based learning product is complete when:

- outcomes and assessments align;
- content is approved;
- visual hierarchy is consistent;
- interactions work;
- accessibility checks are complete;
- media has captions/alternatives;
- source rights are documented;
- package/tracking works in the target LMS;
- pilot issues are resolved or accepted;
- version and ownership are recorded.

## Capstone - Build an evidence-based digital learning module

### Scenario

You are the instructional designer for a technology academy. You must transform a subject-matter expert's six-page technical briefing into a **15-20 screen self-paced learning module** for adult learners.

Choose one approved topic such as:

- secure passwordless authentication;
- cloud shared responsibility;
- IPv4 subnetting fundamentals;
- data classification;
- API request/response fundamentals;
- safe use of generative AI;
- accessibility fundamentals;
- incident reporting workflow.

### Required deliverables

Create all of the following:

1. **Learning architecture brief** - audience, context, prerequisites and capability outcome.
2. **Alignment matrix** - outcomes, evidence, practice and assessment.
3. **Content-priority map** - must perform / must know / should know / could know.
4. **Storyboard** - minimum 15 screens including purpose, visual, narration, interaction, accessibility and tracking fields.
5. **Production deck/module** - minimum 15 completed screens in a tool of your choice.
6. **Visual explanation** - at least one original diagram or concept map.
7. **Worked example** - at least one fully worked example followed by learner practice.
8. **Interaction** - at least one meaningful scenario, classification, sequence or decision activity.
9. **Retrieval practice** - at least two non-identical knowledge retrieval opportunities.
10. **Narration/media script** - required for any audio/video used.
11. **Accessibility pack** - titles, reading-order evidence, alt-text register, contrast check, caption/transcript evidence and keyboard test.
12. **Media rights register** - source, creator, licence and attribution for external assets.
13. **Publishing manifest** - target platform, package type, completion rule, pass rule and version.
14. **Tracking map** - SCORM status assumptions and/or xAPI event plan.
15. **Usability test report** - at least two pilot users or structured peer reviews, findings and revisions.
16. **Design rationale** - 800-1,200 words connecting decisions to cognitive load, multimedia learning, accessibility and assessment alignment.

### Capstone storyboard template

```text
Screen ID:
Purpose:
Outcome supported:
On-screen title:
On-screen copy:
Visual treatment:
Narration/facilitator note:
Learner action:
Feedback:
Accessibility:
Tracking:
Source/rights:
Status: Draft / Review / Approved / Built / Tested
```

### Capstone design-review checklist

**Learning architecture**
- Is the terminal outcome observable?
- Does the final assessment require the learner to demonstrate the outcome?
- Does every screen contribute to the learning path?

**Cognitive load**
- Is unnecessary content removed?
- Are complex ideas segmented?
- Are labels close to the relevant visual?
- Is narration coordinated with the visual rather than duplicated?

**Visual design**
- Is hierarchy obvious?
- Are text and visuals readable at intended viewing size?
- Is the layout consistent?
- Does every meaningful visual teach something?

**Interactivity**
- Does the learner retrieve, decide, classify, construct or diagnose?
- Does feedback explain the reasoning?
- Can the learner recover from error?

**Accessibility**
- Unique titles?
- Logical reading order?
- Alternative text/equivalent descriptions?
- Captions/transcripts?
- Keyboard operation?
- Non-colour cues?
- Sufficient contrast?

**Production**
- Version identified?
- Source rights documented?
- LMS completion verified?
- Resume/retry behaviour tested?
- Analytics events validated?

### Assessment rubric

| Criterion | Weight | Competent evidence |
|---|---:|---|
| Learning architecture and alignment | 15% | Observable outcomes, aligned evidence and coherent sequence |
| Cognitive-load and multimedia design | 15% | Deliberate chunking, signaling, contiguity, segmentation and justified media use |
| Visual communication | 15% | Strong hierarchy, readable typography, explanatory visuals and consistent design system |
| Interaction and practice | 15% | Meaningful learner decisions, retrieval practice and instructive feedback |
| Accessibility and inclusion | 15% | Titles, reading order, alternatives, captions, keyboard operation and documented testing |
| Production quality and tool use | 10% | Stable implementation, reusable patterns and controlled media/assets |
| LMS/tracking readiness | 5% | Explicit completion/pass rules and validated publishing/tracking plan |
| Evaluation and iteration | 5% | Pilot evidence, defect log and justified revisions |
| Design rationale and evidence portfolio | 5% | Clear traceability from principle to design decision |

### Competence threshold

A learner is **capable** when the submitted module demonstrates not only visual polish but repeatable design judgement. The learner must be able to explain why each major design decision supports the outcome, reduces a barrier, improves comprehension or strengthens evidence of learning.

## Tool-maintenance and standards note

PowerPoint, Google Slides, Articulate Storyline, Adobe Captivate, LMS products and accessibility tooling change over time. Accessibility conformance claims are also version-specific. Before a production release, verify the current product documentation, target LMS behaviour, browser/assistive-technology support and the current accessibility conformance report for the exact authoring tool version being used.

SCORM remains widely deployed across LMS environments, while xAPI 2.0 is the current Experience API specification. The course therefore teaches **publishing architecture and validation** rather than assuming one package profile is correct for every LMS.
