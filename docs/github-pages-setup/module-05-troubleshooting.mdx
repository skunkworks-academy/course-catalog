- Distinguish build, artifact, DNS, certificate and client-side routing failures.
- Produce a concise root-cause analysis with verified corrective action.

## Guided lesson

### Diagnostic sequence

1. **Source:** Is the expected commit on the deployment branch?
2. **Trigger:** Did the workflow run for the correct event?
3. **Build:** Did dependency installation and static generation succeed?
4. **Artefact:** Does the uploaded artefact contain `index.html` at its root?
5. **Deployment:** Did the Pages environment deployment succeed?
6. **Routing:** Are base paths and trailing-slash assumptions correct?
7. **DNS:** Does the hostname resolve to the intended Pages target?
8. **TLS:** Is the certificate issued and HTTPS enforced?
9. **Browser:** Is cache, service-worker state or mixed content masking the fix?

### Failure scenarios

#### Scenario A — Workflow succeeds, site returns 404

Check the Pages source is set to **GitHub Actions**, the artefact root, `baseUrl`, case-sensitive file paths and deployment URL.

#### Scenario B — Custom domain says “improperly configured”

Check the repository custom-domain value, DNS record type, target value, duplicate records, proxy/CDN settings and resolver propagation.

#### Scenario C — HTTPS option unavailable

Confirm DNS is valid, the custom domain is attached, CAA records permit the certificate authority and sufficient issuance time has elapsed.

#### Scenario D — Assets fail only on project URL

Search for absolute paths beginning with `/`. Replace them with generator-aware paths that include the repository base path.

## Applied exercise and assessment evidence

**Task.** Inject one safe failure: invalid baseUrl, missing artifact output, incorrect DNS target in a simulated change plan, or a broken deep link. Capture the expected behavior, actual results, diagnostic commands, fix and evidence that the issue is resolved.

**What to submit.** An evidence pack containing the configuration or plan, a short annotated diagram, command or workflow outputs where applicable, sanitized screenshots or illustrative figures explicitly labeled as simulations, and a one-paragraph reflection on failures or operational risks.

**Acceptance criteria.** A different engineer can reproduce the fault, understand the root cause and independently verify the remediation.

**Assessor checkpoints.** Confirm technical correctness; verify that screenshots and logs identify the environment and date; ensure commands are reproducible; and confirm no credentials, personal data, private courseware or customer secrets are included.

Submit confidential work to an approved authenticated LMS or evidence repository, not to a public Pages artifact.
:::
